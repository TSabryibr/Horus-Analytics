🔍 Findings

🟡 P1: Freshness Cache Not Invalidated After Scanner-Triggered Sync

DailyScanner._maybe_sync_intraday() calls ingest_intraday() directly (line 114) but does NOT call invalidate_freshness_cache() afterwards. The sync_all() path does invalidate the cache, but the scanner bypasses it. Other consumers (pipeline worker, data status API) see stale freshness for up to 60 seconds.

File: core/DailyScanner.py:114-115

Fix: Add from data_engine.freshness import invalidate_freshness_cache and call invalidate_freshness_cache() after ingest_intraday.ingest_intraday().

⚪ P3: Three Independent Timers Not Phase-Locked

Harvester (5m) → Pipeline Worker (adaptive) → Scanner sync (5m) operate on independent clocks. In worst case, data flows through 3 async hops. Inherent in the async architecture; no practical fix needed.

⚪ P3: Frontend Refresh Mechanism Not Audited

How dashboard tabs know when to re-fetch data status was not in scope. If polling-based, there's additional display latency beyond the API cache TTL.
